# Arm-Lift — RMA 設計

多様な形状の物体を掴むタスク。方策に**特権情報を圧縮した 16 次元**を条件づけ、後段で深度カメラからそれを推定させる（Rapid Motor Adaptation）。

- 参考論文: [RMA²](../papers/Rapid_Motor_Adaptation_for_Robotic_Manipulator_Arms.md) — 二段構成（§3）、特権情報の内訳（§4）、ランダム化範囲（Tab.2）
- 参考論文: [DextrAH-G](../papers/DextrAH-G_Pixels-to-Action_Dexterous_Arm-Hand_Grasping_with_Geometric_Fabrics.md) — Student アーキテクチャと深度拡張
- 参考実装: `unitree_rl_lab` の `origin/feat/mid360` — `Go2-Blind-GRU-Phase1`（GRU を PPO に差す構成）
- 先行タスク: `Arm-Lift-Cube` — ロボット、基部高さ、腕アクション、報酬重み、初期姿勢カリキュラムはここから継承

タスク ID: **`Arm-Lift`**（teacher）/ `Arm-Lift-Student`（phase 2、未実装）

---

## 1. なぜ二段なのか

```
phase 1 (PPO)         e, s_t ──→ mu ──→ z(16) ─┐
                                               ├──→ pi ──→ action
                      x_t ──────────────────────┘

phase 2 (蒸留)         depth ──→ CNN ─┐
                                      ├──→ phi ──→ ẑ(16) ──→ pi(凍結) ──→ action
                      x_t ──→ GRU ────┘
```

ボトルネックが本体。実機で得られない情報（質量・摩擦・形状）に方策を条件づけたうえで、その条件づけを**深度画像と固有受容感覚の履歴から復元できる程度に小さく滑らかな表現**に絞る。16 次元なのはそのため。

## 2. 特権情報

### `x_t` — 観測（42）

| 項目 | 次元 | 備考 |
|---|---|---|
| `joint_pos` / `joint_vel` | 9 / 9 | 腕 7 + 指 2 |
| `object_position` | 3 | σ=0.02 のガウスノイズ + エピソード固定バイアス |
| `target_object_position` | 7 | ゴール `g` |
| `tcp_to_object` | 3 | 派生量。FK を方策に学習させずに済ませる |
| `object_to_goal` | 3 | 同上 |
| `last_action` | 8 | 腕 7 + グリッパ 1 |

### `e` + `s_t` — 特権（18、埋め込み後 45）

| 項目 | 観測次元 | μ 入力次元 | スケーリング |
|---|---|---|---|
| `object_extent` | 3 | 3 | `/0.05` |
| `object_mass` | 1 | 1 | `/0.2` |
| `object_friction` | 1 | 1 | `(f-0.8)/0.3` |
| `object_category` | 5 (one-hot) | 32 (埋め込み) | — |
| `object_rot_6d` | 6 | 6 | そのまま |
| `finger_contact_force` | 2 | 2 | `log1p(F)/4` |

`z = mu(e, s_t)`、**16 次元**。

### 設計上の判断

**正規化は手でやる。** `empirical_normalization = False`。ランダム化範囲は我々が決めているので固定除数が厳密。走行統計は学習初期に動く的で、このタスクは初期の摂動に脆いことが `SMOOTHNESS_PENALTY_ONSET` の件で分かっている。無対策だと μ の第1層が接触力（数十 N）に支配され、半寸法（0.01 m 台）が消える。

**回転は 6D。** yaw を `[-π, π]` で一様ランダム化しているので、オイラー角や回転ベクトルだと ±π の折り返しを毎エピソード踏む。物理的に 1° の違いで入力が 2π 飛ぶ。SO(3) を連続表現できる最小次元が 6。第3列は外積で復元できるので情報の損失はない。

**カテゴリは one-hot で渡して、モデル側で bias なし Linear に通す。** `nn.Embedding(5,32)` と数学的に同一（one-hot × 重み行列 = 行の取り出し）。この形にしたのは、観測を float のままにできること、学習後に `.weight` をダンプして**どの形状族を方策が近いものとして扱っているかを直接見られる**こと。

**接触力は `log1p`。** 衝突の瞬間にスパイクする裾の重い量で、線形スケールをスパイクに合わせると「触れている／握っている」の低力域が潰れる。

### 入れなかったもの

| 項目 | 理由 |
|---|---|
| instance 埋め込み（論文の主要貢献1） | 残り 5 形状は全部凸で `(category, extent)` で完全記述できる。さらに寸法を連続サンプルするのでインスタンス番号はサイズすら決めず、extent より情報が少ない。論文の NoOE ablation の差 3.4pt は YCB 78 メッシュの話 |
| `rest_pose` 埋め込み | `rot_6d` のどの行が world z に揃っているかで分かる。姿勢が効くのは接近中で、その間は `rot_6d` = 接地姿勢 |
| `object_lin_vel` / `ang_vel` | 論文に無い。滑り検知に有効と考えたが不採用 |
| `object_grasp_width` / `wedge_angle` / `com_height` | `(category, extent)` から導ける。非凸形状（トーラス）用に足したもので、トーラスを外した時点で不要 |
| `tcp_object_surface_dist` | `tcp_to_object` と `extent` から導ける |
| density | mass + 体積と冗長 |
| 外乱力（論文 §4） | 不採用。結果として `object_mass` が効くのは持ち上げる瞬間の重さだけになる |

判断の基準は一貫して「**同じタイムステップでベクトル内の他の要素から導出できるものは入れない**」。

## 3. Teacher NN

```
obs (60) ──split──┬─ x_t (42) ──────────────────────────┐
                  │                                      ├──→ pi MLP[256,128,64] → action (8)
                  └─ priv (18) ──→ mu ──→ z (16) ────────┘

mu     : one-hot(5) → Linear(5, 32, bias=False)
         concat(extent 3, mass 1, friction 1, cat 32, rot6d 6, force 2) = 45
         → MLP[128, 64] → 16
critic : 60 → MLP[256, 128, 64] → 1        （ボトルネックを通さない非対称critic）
```

**rsl-rl への差し込みは `self.actor` の置き換えだけ。** `ActorCritic._update_distribution` は `mean = self.actor(obs)` を呼ぶだけで、`obs` は `get_actor_obs` が `obs_groups["policy"]` を順に concat したもの（`rsl_rl/modules/actor_critic.py:166`）。なので

```python
obs_groups = {"policy": ["policy", "privileged"], "critic": ["policy", "privileged"]}
```

とし、`self.actor` を `RmaActor` に差し替える。`act` / `act_inference` / `evaluate` / critic は無改造。critic がこの連結をそのまま食うので、**生の特権ベクトルを見る非対称critic が副産物で手に入る**。

特権グループは **obs_groups の末尾固定**。actor が末尾から幅で切り出すため。`RmaActorCritic.__init__` がこれを検査する。

**μ は π より小さい `[128, 64]`。** 入力は既に手で選んだ意味の通った 45 次元で、知覚する対象がない。圧縮と混合だけ。広くすると 5 行の埋め込みテーブルを覚え込むだけになる。論文も μ は 3 層、π は 4 層。

**π は `[256,128,64]` のまま。** cube teacher が 36 次元入力でこの構成で収束している。入力が 58 に増えるだけで、周りを作り直す理由がない（`unitree_rl_lab` の `GruPPORunnerCfg` も同じ規律で再帰だけ差している）。

パラメータは actor 約 71k（cube teacher は 51k）、critic 約 56k。

## 4. Student NN（phase 2）

```
depth(60x80) → CNN[16,32,64] → head[128] ──┐
                                           ├→ MLP[256,128] → ẑ(16) → pi(凍結) → action(8)
x_t(42) → GRU(hidden 128, 1層) ────────────┘
```

**CNN は RNN を通さない。** 画像は瞬時の幾何、履歴は動特性で、役割が違う。視覚特徴を隠れ状態に担がせると学習が重くなるだけ。

**履歴が必須。** 現 student は固定カメラを根拠に単フレーム・非再帰だが、その根拠は推定対象が `object_position` だったから。質量と摩擦は接触してから押し返されるまでの応答にしか現れず、**単フレームでは原理的に出ない**。

**`gradient_length = 24`（cube タスクは 4）。** 非再帰なら単なるミニバッチ化だったが、再帰だとこれが BPTT 窓になる（`rsl_rl/algorithms/distillation.py:138` が `gradient_length` ごとに `backward()` → `detach_hidden_states()`）。4 ステップ = 0.08 秒では接触イベント 1 つ収まらず、長期記憶を使う動機が発生しないので GRU が実質 MLP になる。24 = 0.48 秒。`num_steps_per_env` と一致させる（`num_steps_per_env % gradient_length == 0` が必要）。隠れ状態は detach されるだけで reset されないので、記憶の射程はエピソード全体のまま。

**環境数は 128**（cube タスクの student は 256）。律速がレンダリングから後退グラフに移る。24 ステップ分の CNN 中間活性を保持するので、1枚あたり約 0.67 MB × 256 環境 × 24 = 約 4 GB となり、レンダラの約 6 GB と合わせて 16 GB を溢れる。履歴長は再帰に必要だがバッチ幅は必要ない、という判断で幅を半分にした。

**teacher の π は明示的に凍結する。** rsl-rl は teacher に `.eval()` を呼ぶだけで、これは標準構成では十分（`evaluate()` が `no_grad` の中にあるため）。この設計では π が勾配経路の中にいる（ẑ が行動損失に届く唯一の経路）うえ、オプティマイザが `policy.parameters()` 全体を取るので、`requires_grad_(False)` を入れないと**行動BC が teacher を student に迎合する方向に書き換える**。

**損失は行動BC 主 + `‖ẑ − z*‖²` aux。** この構造だと `act_inference` が action を返すので rsl-rl の行動BC がそのまま効き、z 回帰を足すだけで済む。既存の `object_position` 回帰 aux も残す。

**GRU（LSTM でなく）、1層。** Miki et al. と `Go2-Blind-GRU-Phase1` に合わせる。hidden は Go2 が 256、こちらは 128 から。Go2 は盲目で接触履歴だけから地形を推定するので記憶の負荷が重いが、こちらは深度が幾何を直接渡すので GRU が担うのは質量・摩擦だけ。

## 5. 物体カタログ

`object_catalog.py`。5 カテゴリ × 40 = **200 プロトタイプ**を固定シード（`CATALOG_SEED`）で一度だけ引き、カテゴリ順にインターリーブして並べる。

**形状は実行中に変えられない。** `MultiAssetSpawnerCfg` は prim 生成時に `assets_cfg[i % len]` を割り当てる（`random_choice=False`、`sim/spawners/wrappers/wrappers.py:110`）。「寸法を連続サンプル」は「200 個を前もって引いて env に配る」という意味にしかならない。

| | env ごとに1回（run 全体で固定） | エピソードごと |
|---|---|---|
| | category、寸法 | mass、friction、接地姿勢 |

| カテゴリ | パラメータ範囲 (m) | 安定姿勢 |
|---|---|---|
| cuboid | 最小半寸法 0.010–0.022、他2軸はその 1.0–2.2 倍（上限 0.040） | 3（どの面で寝るか） |
| cylinder | r 0.010–0.022、h 0.030–0.070 | 2（立つ / 横倒し） |
| capsule | r 0.010–0.020、h 0.020–0.050 | 2 |
| sphere | r 0.014–0.030 | 1 |
| cone | r 0.016–0.032、h 0.038–0.070 | 2（底面 / 横倒し） |

### Cone を入れた理由と、それが外れたこと

当初の予測：円錐は半頂角 `α = atan(r/h)` の楔をグリッパに見せ、素直に握って保持できる条件は `tan α < μ`。

```
摩擦 μ=[0.50, 1.10]  →  自己ロック限界 α = [26.6°, 47.7°]
カタログの cone        →  α ≈ 15°〜40°、保持に必要な μ = 0.28〜0.84
```

必要 μ がランダム化範囲の内側に落ちるので、同じ物体でも引いた摩擦次第で成否が変わるはず、という理屈だった。これが `object_friction` を特権情報に入れる唯一の正当化でもあった。

**測定で否定された。** 摩擦ビン別の成功率（1201エピソード、5cm以内）:

| μ | placed | | μ | placed |
|---|---|---|---|---|
| 0.50–0.65 | 80.5% | | 0.80–0.95 | 77.6% |
| 0.65–0.80 | 76.6% | | 0.95–1.10 | 78.0% |

フラットで、最低摩擦ビンがわずかに最良。予測と逆向き。球も同様。

一方で**接地姿勢は相関する**（底面 72.8% / 横倒し 83.3%）。楔を上向きに見せる姿勢のほうが 10.5 ポイント悪い。幾何は関与していて係数は関与していない、という形。連続グリッパが十分な握力を出せるので [0.50, 1.10] の全域で μ が律速になっていない、というのが有力だが未検証。`object_friction` は現状、測定に裏付けのない特権入力として残っている（18次元中の1なので外す理由も強くない）。

### 接地姿勢

`reset_object_stable_pose`。`reset_root_state_uniform` の連続 roll/pitch は**使えない**（非平衡姿勢で落とすのでエピソード冒頭に転がる、かつ接地 z を姿勢に連動させられない）。離散の安定姿勢から一様に引き、world 鉛直まわりの yaw を掛ける。

横倒しの円柱・カプセルは軸まわりに中立平衡なので、指が偏って当たれば転がって逃げる。横倒しの円錐は頂点を中心に円弧を描いて転がる。

円錐の横倒し姿勢は解析的に出す。斜線が水平になるのは軸が `α` だけ**下に**傾いたとき（頂点が接地、太い側が上）で、原点は `(h/2)·sin α` の高さに来る。「頂点の高さ = 底面リム最下点の高さ」を解くとそうなる。y 軸まわり `90° + α` の回転。

### トーラス（検討して不採用）

IsaacLab にも USD にもトーラスは無く、メッシュで作るしかない。`meshes.py:356` が衝突近似をクラス名でハードコードしていて、既定は `convexHull` — **トーラスの凸包は原点を含む**ので穴が完全に埋まる。見た目だけドーナツで指が通らない。`ConvexDecompositionPropertiesCfg` を当てる自作 spawner を書けば可能だが、保留。

## 6. 環境側の変更

### lift ゲートを接地高さ基準に

絶対 z 0.04 m 固定をやめ、`接地高さ + 0.02 m`（`lift_threshold`）。混合カタログで絶対閾値を使うと形状ごとに要求される仕事量が変わる。

```
立位の円柱 (h=5.5cm)  接地 2.75cm → 1.25cm 上げれば合格
球 (r=1.5cm)          接地 1.50cm → 2.50cm 上げないと不合格
```

方策は背の高い物体を選ぶことを学習し、形状別成功率も比較できなくなる。`lifting_object` / `object_goal_tracking` / `fine_grained` の3項が同じゲートを使う。

テーブル上面は **world z = −0.003 m**（`TABLE_TOP_Z`）。視覚面ではなくコライダー面で、既知寸法のプリミティブを落として実測した（半高さちょうど −3.0 mm、4.2〜8.4 cm のサイズと `rest_offset` ∈ {default, 0.0, −0.003, +0.010} で不変なので接触オフセットではない）。配置は接地高さ +2 mm で、誤差があっても 2 mm 落ちるだけで貫通しない。

### グリッパを連続値に

`MimicJointPositionAction`（自作、1 アクション → 両指に同じ目標）。

```
action ∈ [-1, 1]  →  目標指位置 = [-0.020, 0.044]
```

二値 `BinaryJointPositionActionCfg` では**握力が方策の選択ではない**。指は implicit actuator なので握力は `stiffness × (目標 − 実位置)` で、目標が 0.0 固定だと `2000 × 物体の半幅` になる。細い物体は弱く、太い物体は強く握られる。

cube タスクでの実測：全形状で接近・把持は 100% 成功し、把持後に落とす率が把持幅と単調対応（3.8cm→3.1%、2.2cm→25.8%）。閉じ指令を −0.01 にするだけで**再学習なしに** 90.2% → 92.1%。下限を −0.020 で止めたのは −0.04 が精度を落としたため（5cm 以内が 84.2% → 78.3%、締めるときに物体が押し出される）。

連続化は `object_mass` / `object_friction` に行動の受け皿を与えるためでもある。これが無いと方策は「滑りやすい」と教えられて何もできない。

左右独立（2 次元）にしなかったのは、非対称把持が「握力が足りていなかったのか」の切り分けを濁すため。対称でまず握力だけを可変にする。

### 接触センサ

`ContactSensorCfg` を `openarm_.*_finger` に。robot 側の spawn で `activate_contact_sensors = True` が要る（無いとセンサは 0 を返す）。

### カタログの遅延初期化

`object_catalog(env)` は**初回アクセス時に構築**する。startup イベントにできないのは、`ManagerBasedEnv.__init__` が startup イベントより先に `load_managers()` を呼び、観測マネージャが次元解決のために全項を1回評価するため。`sim.reset()` は済んでいるので PhysX view は生きている。

env → カタログの対応は、spawner が使ったのと同じ `find_matching_prim_paths` を引き直し、**パスから env 番号をパースして**決める（`env_10` が `env_2` より前に来る可能性があり、列挙順 = env 番号とは限らない）。決まった対応は PhysX が報告する質量と突き合わせて検証する。ここを間違えても何も落ちず、別の物体の寸法で静かに学習してしまうため。

## 7. ランダム化（論文 Tab.2 準拠）

| | 範囲 | 頻度 |
|---|---|---|
| density | 公称 1000 kg/m³ の ×[0.5, 5.0] | エピソードごと |
| friction | [0.50, 1.10]（静＝動） | エピソードごと |
| 寸法 | §5 の範囲から連続 | env ごとに1回 |
| 物体位置 | x (-0.10, 0.02) / y (-0.18, 0.18) / yaw 全周 | エピソードごと |
| 腕初期姿勢 | レベル 0–10、±0.2 rad まで | カリキュラム |

`randomize_object_physics` は IsaacLab の `randomize_rigid_body_mass` / `randomize_rigid_body_material` を使わず自前。どちらも**引いた値を返さない**のに、両方とも特権観測に出す必要があるため。方策に教える値とソルバが使う値が同じテンソルであることを保証する。

`randomize_rigid_body_scale` は使わない（絶対 scale を書くので公称の違う資産が混ざると壊れる。寸法はカタログに畳み込み済み）。

128 環境、teacher は `arm_lift/2026-10-14_10-55-01_rma_v1/model_4999.pt`、5000 イテレーション。

| it | behavior | latent | objpos | reward | lift |
|---|---|---|---|---|---|
| 0 | 0.3003 | 0.1528 | 0.0422 | 0.03 | 0.00 |
| 1000 | 0.1466 | 0.0446 | 0.0035 | 131.49 | 12.63 |
| 3000 | 0.0846 | 0.0304 | 0.0036 | 118.76 | 12.11 |
| 4000 | 0.0795 | 0.0258 | 0.0025 | 127.95 | 12.13 |
| 4999 | 0.1040 | 0.0303 | 0.0033 | 119.67 | 10.62 |

`latent loss` が 0.153 → 0.026。`z*` の実測が mean |z| 0.32 / max 1.23 なので、深度と固有受容感覚の履歴から16次元が復元できている。GRU の hidden を 256 に上げる必要は今のところ無い。

末期に損失が悪化している（behavior 0.0795 → 0.1040）が、**行動の質には現れなかった**。`model_4000.pt` と `model_4999.pt` を同条件で測ると 85.1% と 85.2% で区別がつかない。損失値だけで劣化と判断しないこと。

直方体・円柱・カプセルは teacher 比 ±1 ポイント以内。論文の Oracle 75.4 → RMA² 73.8（1.6 ポイント差）と同程度の落ち幅。

損失は球と円錐に集中し、特に**横倒しの円錐が 83.3% → 66.3%**（teacher → student）で最大。横倒しの円錐は頂点の向きで掴み方が変わる唯一の形状で、teacher は `rot_6d` で直接知るが student は 80×60 の深度から推定するしかない。横倒しの円柱（94.2%）が落ちないのは軸対称だから、という説明は筋が通るが**未検証**。

比較の条件差を1つ。teacher の評価は `object_position` に σ=0.02 のノイズが乗った状態、student は乗っていない（蒸留タスクは観測をクリーンにしている）。共通項では student のほうが条件が楽なので、−3.0 ポイントは下限寄りの見積もり。

## 12. エクスポート

`rma_student_exporter.py`。出すのは CNN + GRU + head + teacher の π まで。teacher のエンコーダ μ は含まない（student がそれを置き換えるために存在するため）。

```
入力   obs        (batch, 4842)    x_t 42 + depth 80x60
       hidden_in  (1, batch, 128)  エピソード先頭はゼロ、以降は前フレームの出力
出力   actions          (batch, 8)
       object_position  (batch, 3)
       hidden_out (1, batch, 128)
```

Isaac Lab のエクスポータとの違いが2点。

**`torch.jit.script` ではなく `trace`。** script は rsl-rl の `Memory` を処理できない。GRU と LSTM を1クラスで扱うために `hidden_state` が Union 型で、TorchScript が `GRU.forward(hx: Optional[Tensor])` に渡せないと判断する。trace にこの問題は無く、このグラフにはデータ依存の分岐が無い。

**隠れ状態を明示的な入出力にする。** 配備時は1フレームずつ外から呼ばれるので、再帰の状態は呼び出し側が持つ。グラフ内部に隠すと使えない。

実物との一致は検証済み（両方 CPU で max |live - jit| = 0.000e+00、隠れ状態を戻した2フレーム目も一致）。GPU と CPU をまたぐと 1e-4 程度ずれるが、これは fp32 の縮約順序の差。

### teacher はエクスポートしない

`play.py` でスキップする。RMA teacher の actor は質量・摩擦・寸法というシミュレータにしか存在しない入力を読むので、固めても実機で動かない。
